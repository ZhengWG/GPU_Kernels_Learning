# GEMM 分块：同一份数据多用几次

前置：[矩阵乘法定义](../../docs/prerequisites/03-math-for-kernels.md)、[存储与数据访问](../../docs/hardware/memory.md)。本页只分析算法，不给出 GPU 实测结论。

## 从一个结果开始

计算 `C = A @ B`，A 为 `M×K`，B 为 `K×N`。直接实现可以让一个线程负责 `C[i,j]`，沿 K 逐项相乘并相加。

```text
原理示意：两个相邻输出会重复使用同一行 A

A 的第 i 行 ── × B 的第 j 列   ──→ C[i,j]
      同一行 ── × B 的第 j+1 列 ──→ C[i,j+1]
```

这两个输出数学上独立，但输入有重叠。分块就是把这些重复使用的数据集中起来。

## 一个线程块负责一个输出块

这里用 `BM、BN、BK` 表示分块的三条边长：

```text
原理示意：沿 K 分两段，相乘结果累加到同一块 C

A 的 BM 行： [ A0 | A1 ]        B 的 BN 列： [ B0 ]
                                           [ B1 ]

C块 = A0 × B0 + A1 × B1

A0: BM×BK，B0: BK×BN，C块: BM×BN
```

每轮把 A、B 的一小块搬到共享内存，块内线程一起使用。C 的中间结果留在线程中，等 K 方向全部计算完再写回。成熟实现也使用多层分块，把块、warp 和更小的计算对应起来。[CUTLASS GEMM 结构](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/efficient_gemm.html)

## 手算一次复用量

假设算一个 `4×4` 输出块，K 为 4，暂时忽略缓存：

| 方法 | 程序请求的输入元素数 | 输出数 |
| --- | --- | --- |
| 每个输出独立读 A 和 B | 16 个输出 × 8 个输入 = 128 | 16 |
| A、B 各搬一份到共享内存 | 4×4 + 4×4 = 32 | 16 |

算法层面的输入读取请求减少到四分之一。这不代表耗时必然降低四倍：缓存本来可能提供复用，还新增了共享内存读写和同步。

一般地，一轮搬入 `BM*BK + BK*BN` 个元素，完成约 `2*BM*BN*BK` 次运算。固定 BM、BN 时，同时增大 BK 会同比增加两者，因此它不会单独提高这个比值。

## 线程里再留一小块结果

```text
原理示意：一个线程累加 2×2 个结果，每次取两个 A 值和两个 B 值

                 b0           b1
             ┌──────────┬──────────┐
        a0   │ c00+=a0*b0│ c01+=a0*b1│
             ├──────────┼──────────┤
        a1   │ c10+=a1*b0│ c11+=a1*b1│
             └──────────┴──────────┘
```

4 个输入值参与 4 次乘加，每个输入用两次。代价是保留更多中间结果，消耗更多寄存器。这里画的是普通逐线程计算，不是 Tensor Core 指令的线程分工。

## 尾部与同步

若矩阵不能整齐分块，越界输入按 0 参与，越界输出不写回。使用共享内存时，一轮通常包含：

```mermaid
flowchart LR
    A[协作读取有效输入，尾部补零] --> B[等本轮数据准备好]
    B --> C[计算并累加]
    C --> D[等所有读取完成]
    D --> E[缓冲区才可装下一块]
```

原理示意。不能因为某个线程的输出越界，就让它提前跳过其他线程需要的共享数据搬运或同步。

## 自测

1. BM、BN 不变，BK 加倍，单轮输入复用比一定提高吗？
2. `M=5、N=7`，输出分块为 `4×4`，需要几块？

<details>
<summary>参考答案</summary>

1. 不提高；可能减少循环次数，但增加共享内存占用。
2. `ceil(5/4)*ceil(7/4)=4` 块，其中三块含边界，需要检查。

</details>
