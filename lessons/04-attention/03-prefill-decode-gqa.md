# Prefill、Decode 与 GQA：同一公式，不同工作量

**查询数量变了，计算与读数据的比例也会变。** 前置：[Attention 分块融合](02-tiled-attention.md)。

## 两个阶段

```text
原理示意：一次处理一条序列

Prefill：处理输入段
Q：很多行  ──→ 计算各输入位置的结果
K、V：为输入位置生成并保留

Decode：每次生成一个新位置
Q：通常只有一行 ──→ 读取已有 K、V，并加入本次的新 K、V
```

KV cache 指保留过去位置的 K、V，避免每次重新计算它们。这里只描述常见自回归推理；批量推理、分块输入或一次处理多个新位置会改变尺寸。

对于单个查询头，历史长度 L、维度 D，令 V 维度也为 D。一次新查询约需 `4*L*D` 次运算，并读取约 `2*L*D*b` 字节 K/V，其中 b 为每元素字节数；忽略缓存、其他读写和 Softmax 计算。

比值约为 `2/b` 次运算/字节。这个粗略例子说明单查询时的数据复用机会较少，但不直接证明某个实际 kernel 的瓶颈。

## 多个查询头共用 K、V

假设 8 个查询头、2 个 K/V 头，按连续分组：

```text
原理示意

Q头 0、1、2、3 ──→ K/V头 0
Q头 4、5、6、7 ──→ K/V头 1
```

这称为 GQA；每个查询头仍有自己的分数和输出。它减少 K/V 头数与缓存存储量；实际 kernel 是否把一次 K/V 读取复用于多个查询头，取决于线程安排。[GQA 原论文](https://arxiv.org/abs/2305.13245)

在相同序列长度和每头维度下，上例 K/V 存储是 8 个独立 K/V 头的四分之一。不能据此承诺 Attention 时间也缩短四倍。

## 掩码需要全局位置

查询只包含最后两个位置、K 有五个位置时，若约定查询位置是 3、4：

```text
              K0 K1 K2 K3 K4
Q全局位置3     ✓  ✓  ✓  ✓  ·
Q全局位置4     ✓  ✓  ✓  ✓  ✓
```

此时直接用局部 `j<=i` 就错了。要根据接口规定查询起点、缓存长度和位置编号。后续读上游接口时，首先对齐这一约定。

<details>
<summary>练习答案</summary>

四个 Q 头均映射到 KV 头 0。若使用绝对查询位置且采用因果掩码，位置 0 仅能看 K0，位置 3 能看 K0..K3（前提是这些键有效）。共享 KV 头不改变每个查询的可见位置。
